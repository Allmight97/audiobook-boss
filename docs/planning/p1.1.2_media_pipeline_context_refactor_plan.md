# Plan: Refactor `media_pipeline.rs` to use a context struct for inner processing functions

Task: P1.1.2  
Branch: `feat/media-pipeline-context`  
Source: `docs/planning/consolidated-roadmap.md` (P1.1.2)  
Goal: Reduce excessive parameter lists in inner functions and remove `too_many_arguments` allows while preserving behavior and test coverage.

Reference: Use `docs/planning/archive_completed/p1.1.1_processor_split_plan.md` as a structural guide for phases, decisions, and acceptance criteria.

## Finalized Decisions (Proposed)
- Introduce a private context struct (`FramePipelineCtx<'a>`) in `media_pipeline.rs` to carry environment, output stream params, and progress state.
- Keep heavy mutable handles (`decoder`, `encoder`, `resampler`, `output_context`) as separate `&mut` params to avoid borrow conflicts.
- Precompute values currently pulled from `plan` and loop state (`total_files`, `total_duration`, `target_sample_rate`, `output_stream_index`, `output_time_base`) and store them in the context.
- Update the three target functions to accept a single `&mut FramePipelineCtx` plus their minimal object params, removing `#[allow(clippy::too_many_arguments)]` on each.
- Optional (Recommended): Also adapt `flush_decoder_frames` to accept `&mut FramePipelineCtx` for consistency and to remove its `too_many_arguments` allowance.

## Naming choice: `FramePipelineCtx` (recommended)
- Pros: Clear scope within frame/packet loops; discourages misuse elsewhere; matches call sites.
- Cons: May need renaming if scope broadens later.

Alternatives considered: `MediaPipelineCtx` (broader, but ambiguous), `ProcessingLoopCtx` (accurate, less specific than "frame").

## Fold `flush_decoder_frames` into the same context?
- Pros: Consistent signatures; removes another allowance; cohesive module.
- Cons: Slightly larger diff.

Decision: Include in this task (Phase 6) to keep the module unified.

- Function length creeping >60 lines: Extract focused helper(s) without behavior change.
