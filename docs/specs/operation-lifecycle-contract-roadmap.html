Operation Lifecycle Contract: Before / After

The open question is whether ABB should name operation lifecycle facts explicitly, instead of letting processing, metadata save, and status panel infer them from separate call choreography.

Short Answer

Accepted choice: introduce bounded lifecycle vocabulary inside processing, probably including an operation kind and shared result-summary vocabulary.

Why: the behavior already exists. Naming it makes the repo more agent-first because future work can ask "what operation is this?" and "what terminal truth did it produce?" without reading three unrelated flows.

Before And After Shape

Before: Truth By Choreography

current code shape

Processing runner run.rs

Owns merge/batch dispatch, job registration, queue emit, terminal result mapping, and audio execution handoff.

shares some primitives, but not a named contract

Metadata save save_batch.rs

Uses JobRegistry, ProgressEvent, QueueEvent, and ProcessResultSummary, then emits events by hand.

event names and progress bands come from the wrong house

Audio constants audio/constants.rs

Holds processing-progress, processing-queue, progress percentages, plus actual audio/media constants.

status kind is set out-of-band

Status Panel Runtime

Consumes progress/queue events, but also relies on callers setting currentWorkKind before events arrive.

After: Truth By Contract

intended roadmap shape

Backend Lifecycle strip processing::lifecycle

Named sub-owner inside processing for job identity, cancellation, queue snapshots, progress events, operation kind, and terminal summary vocabulary.

processing and metadata save call the same lifecycle language

Processing runner run.rs

Keeps processing-specific work: preflight/run dispatch, output-plan interaction, and audio engine request assembly.

Metadata save save_batch.rs

Keeps metadata policy in metadata, but reports lifecycle truth through the lifecycle strip instead of hand-building a parallel path.

Progress/events owner

Event names and progress math live beside ProgressEvent, QueueEvent, and emit helpers, not under audio.

Status Panel Runtime

Stays a consumer/read model. If backend events include operation kind, it can consume that fact instead of relying only on caller choreography.

What Q1 Actually Changes

Choice What It Means Upside Cost / Risk
No new vocabulary
Move constants only		 Keep existing JobType, ProcessResultSummary, metadata-specific result status, and UI currentWorkKind. Smallest contract churn. Leaves future agents asking why metadata uses processing result summary and why status kind lives outside event truth.
Bounded vocabulary
Accepted		 Add lifecycle-level terms such as OperationKind and shared terminal summary vocabulary under processing lifecycle. Makes the operation contract visible and reusable without inventing a new platform. May require generated binding churn and careful Status Panel consumption updates.
Generic operation framework
Avoid		 Abstract everything into a broad operation manager that tries to own processing, metadata, audio, and status. Looks tidy on paper. Creates the blob we explicitly do not want.

Lifecycle Flow After The Roadmap

1. Operation starts

Processing or metadata save declares the operation kind and registers lifecycle state.

2. Queue truth emits

Queue snapshot is built through lifecycle-owned event types and names.

3. Progress truth emits

Stage, percentage, job id, input index, and current file use one lifecycle vocabulary.

4. Terminal truth resolves

Success, skipped, cancelled, and failed produce shared summary shape without hiding owner-specific details.

5. Status consumes

Status Panel renders the read model. It does not become the backend operation owner.

Accepted Decision To Carry Forward

Use bounded lifecycle vocabulary when it removes call choreography and improves agent readability. The stop rule is simple: if an abstraction starts hiding processing, metadata, audio, output artifact, or status ownership, it is too broad.
