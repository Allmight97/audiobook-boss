ABB Greenfield Convergence via Effect

A forest-level adoption roadmap: move current ABB toward the greenfield shape, then turn each milestone into a one-PR design shape on the roadmap branch.

Recommendation

Adopt Effect if the target is ABB's TypeScript workflow operating model, not a blanket rewrite. Effect should own async orchestration, typed workflow errors, dependency injection, resource lifetime, retries, streams, and test harness seams.

The destination is current ABB moved as close as practical to the greenfield shape: Rust owns durable truth, Svelte renders, Effect owns workflow coordination, Specta guards the TS-Rust contract, and tauriClient stays the boring runtime adapter.

Workflow owners Move multi-boundary coordination out of UI modules and into named Effect workflows.
Boring boundaries Specta and tauriClient stay mechanical: enough protection, no clever glue.
Make agents stronger Workflow owners, services, typed errors, and fake layers become easy to locate.

M3
Workflow owner

ProcessingWorkflow Extraction

Remove the largest frontend orchestration glue surface by giving status processing an explicit workflow owner.

  • Extract ProcessingWorkflow from src/ui/statusPanel/processing.ts.
  • Move output review, metadata staging, progress startup, IPC processing, cancellation, terminal result handling, and status feedback into the workflow owner.
  • Keep Status Panel Runtime responsible for renderable status truth and user interaction.
  • Include progress subscription lifetime if needed for coherent cleanup.
Exit gate: equivalent behavior, stable public strips, and workflow tests for status, cleanup, cancellation, typed errors, and terminal outcomes.
M4
Metadata boundary

MetadataSaveWorkflow And Intent Staging

Reduce metadata boundary ambiguity without pretending the TS-Rust metadata boundary can disappear.

  • Extract MetadataSaveWorkflow around metadata save and intent staging.
  • Preserve frontend draft/validation behavior while Rust remains metadata write truth.
  • Centralize typed save errors, save-progress state transitions, and boundary calls.
  • Clarify editable intent, command payload, generated contract shape, and persisted artifact truth.
Exit gate: equivalent save behavior, clear contract parity, and tests for success, typed failure, cleanup, and no generated-binding reach-through.
M5
Future feature ingress

Future Workflow Ingress Rule

Prevent future feature work from reintroducing frontend orchestration glue while keeping feature roadmaps separate.

  • After M2, new frontend work coordinating multiple real boundaries starts with an explicit Effect workflow owner.
  • Name RemoteAcquisitionWorkflow as a likely future consumer without implementing that feature set here.
  • Sketch auth, library scan, progress, cancellation, import handoff, and logout/purge service ports only if needed for roadmap alignment.
  • Keep tokens, provider internals, acquisition lifecycle, and artifact truth with the Rust/Remote Acquisition feature design.
  • Exclude live provider proof and user-facing feature delivery unless a separate feature roadmap PR intentionally combines them.
Exit gate: future feature work has a clear ingress rule: use a workflow owner for multi-boundary orchestration, or document why the work is local and boring enough to stay plain.

M8
Guardrails

Boundary Guardrails, Docs, And Opportunistic Script Hardening

Lock in the operating model only where it changes future behavior.

  • Harden guardrail scripts only when a milestone opens that script surface for a real boundary reason.

Greenfield Convergence Review

Greenfield Frontend Frame

Question current frontend choices without destabilizing settled backend truth.

Stack Decision Matrix

From a true greenfield frontend view, the recommendation is still TypeScript + Effect + Svelte + Tauri. The Svelte choice is contextual and nuanced, not a universal renderer win.

Greenfield convergence target: keep the real Rust/Tauri/TypeScript boundary, then remove accidental frontend coordination by giving workflows explicit owners. Effect is the workflow runtime; it is not a renderer, IPC generator, or replacement for Rust truth.
Layer Recommendation Serious alternatives Why this default holds
Frontend language TypeScript Plain JS, Rust/WASM UI, Dart/Flutter, Elm/ReScript/Kotlin JS Effect is TypeScript-native, Specta/Tauri produce TS-facing contracts, and agents get checkable payload shapes.
Workflow runtime Effect Promise-only modules, RxJS, XState, custom services Effect covers typed errors, services, interruption, scoped cleanup, retry, streams, and fake layers in one model.
Renderer Svelte React, Vue, Solid, Web Components, plain DOM Svelte is the best ABB default because the current pain is workflow ownership, not rendering. React is the strongest challenger if ecosystem depth or team fluency dominates.
Desktop shell Tauri Electron, native SwiftUI/AppKit, Flutter desktop Tauri aligns with ABB's Rust core, security/capability boundary, smaller app posture, and no need for Node in the renderer.
TS-Rust contract Tauri + Specta + tauriClient Raw invoke, HTTP localhost API, GraphQL, custom JSON bridge Rust declares the contract, generated TS catches drift, and the handwritten tauriClient adapter centralizes normalization.

Renderer Comparison

A renderer turns state into DOM, events, and pixels inside the Tauri webview. Effect is not a renderer; it is the workflow runtime behind the UI.

Renderer Where it is strong ABB fit Reassess trigger
Svelte Compiler-backed components, HTML/CSS/JS closeness, compact local UI islands. Best current default. ABB's complexity is workflow orchestration, not rendering. Effect-to-Svelte state projection becomes awkward, duplicated, or harder for agents than the workflow itself.
React Largest ecosystem, mature devtools, common large-app patterns, contributor familiarity. Strongest challenger, especially if component-library depth becomes more important than local UI simplicity. UI composition and design-system scale become harder than workflow or IPC complexity.
Vue Approachable templates and a larger ecosystem than Svelte. Plausible, but not a clear ABB-specific improvement over Svelte. Svelte tooling becomes a recurring blocker.
Solid Fine-grained reactivity and JSX-like composition. Technically interesting, but lower continuity and ecosystem fit for ABB. A future UI rewrite wants React-like syntax without React runtime costs.
Web Components Framework-independent custom elements. Useful for isolated widgets, weak as the whole app architecture. ABB needs reusable standalone widgets across renderer boundaries.

Why Svelte Stays

Fit
Svelte keeps ABB screens close to HTML/CSS/TypeScript while Effect owns async workflow logic.
Nuance
This is a narrow ABB decision. React is not wrong; it solves a different center of gravity.
React Wins If
ABB's hardest problem becomes design-system scale, third-party components, or contributor React fluency.

Tauri vs Electron

Electron is credible and can be performant when engineered well. The greenfield reason to keep Tauri is not "Electron is bad"; it is that ABB already wants Rust, a tight IPC boundary, smaller app posture, and no Node runtime in the UI.

Tauri
Best default when Rust backend ownership and app-size/security posture matter.
Electron
Best challenger when identical Chromium behavior, Node ecosystem depth, or Electron-specific desktop tooling matters more.
Watch
Tauri's system WebView can mean platform-specific rendering behavior. That is the real tradeoff to monitor.

TS-Rust Contract Layers

Layer Owner What it does Why keep it
Rust commands/events Rust backend Own durable command shapes, event payloads, app errors, processing truth, and artifact behavior. Rust remains the backend source of truth.
Specta / tauri-specta Generated contract strip Export Rust-declared command/type shapes into TypeScript-facing bindings and expose drift. Solves TS-Rust contract drift without hand-maintaining frontend mirrors.
tauriClient Handwritten adapter Wrap generated calls, normalize payloads, translate errors, centralize events, and expose Promise methods. Keeps UI and workflow modules away from raw invoke strings and generated churn.
Effect services Workflow modules Consume tauriClient through injectable services for workflow errors, cleanup, retries, and tests. Improves orchestration without leaking Effect into Rust or public UI boundaries.
Handwritten client means tauriClient: generated bindings are mechanical contract output; src/lib/tauri/client.ts is ABB's owned adapter for domain naming, error normalization, null/undefined policy, event cleanup shape, and public Promise methods.
Agent-experience read: ABB's grey-box module architecture is still a net positive. It gives agents names for ownership, public strips to protect, and private clusters they can reshape without guessing which caller depends on which helper.

Open Alignment Questions

Question Recommended default Decision impact
Should ProcessingWorkflow definitely precede MetadataSaveWorkflow? Yes by destination fit; switch only if M3 implementation planning proves too wide. Controls whether the first serious conversion attacks the biggest glue surface or starts with a smaller proof.
How should the separate Remote Acquisition roadmap consume this roadmap? Use the M2 workflow-owner shape and M5 ingress rule; keep feature delivery in its own roadmap. Lets future work avoid Promise glue without making this roadmap own uninstantiated features.
Should Specta-generated bindings ever be imported directly by workflows? Default no. Keep generated bindings as adapter input through tauriClient. Preserves boring contract machinery and prevents generated churn from becoming workflow API.
What would make us replace Svelte? Only evidence that state projection becomes awkward, duplicated, or agent-hostile. Keeps greenfield thinking honest without forcing UI churn.
When is remaining glue acceptable? When it is local, boring, tested, and not coordinating multiple real boundaries. Prevents the roadmap from chasing every adapter while still removing architectural glue.
