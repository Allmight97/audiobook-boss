What this roadmap is for

Audio processing is where media execution, toolchain selection, stream integrity, metadata write timing, staging, finalization, cancellation, and progress reporting currently meet. The roadmap should make that meeting point explicit and owned.

The likely destination is a media-engine-shaped boundary: processing coordinates work, audio executes media truth, output artifact commits final files, metadata owns tag outcome, and status runtime renders truthful operation state.

What this roadmap is not for

  • No implementation in this planning thread.
  • No generic operation manager unless evidence forces it.
  • No metadata redesign unless audio discovery exposes a specific contract gap.
  • No fallback behavior without trigger, signal, register entry, and removal condition.

Current-state smell

Media execution is adjacent to too many truths: lifecycle, metadata, artifact commit, status, and external process behavior.

Target-state principle

Each boundary can ask audio for media execution without importing or reimplementing media decisions.

Zoom-in rule

If a before/after row feels fuzzy, zoom into the listed milestone rather than expanding the whole roadmap.

M0 verdict

Use Audio Engine Deep Module as the default owner hypothesis for implementation planning. Keep Operational Status Runtime as audit/decision scope unless source evidence shows audio cannot be made coherent without status-runtime changes.

Public edge finding

Current audio exports mix caller-facing API with internal engine pieces: file info, validation, toolchain detection, cleanup, processor execution, adapter routing, native engine types, preview internals, and processor submodules.

Implementation planning should validate and narrow the strip rather than treating today's export list as the intended API.

Processing lifecycle finding

Processing owns queue/session/cancel identity, execution plan preparation, job registration, terminal normalization, and command results.

It currently reaches into audio for file info and adapter resolution; that is the caller surface the Audio Engine Deep Module should simplify or make explicit.

Finalization finding

Native finalization delegates final commit truth to output_artifact. External FDK repeats staging, metadata rewrite, output commit, cleanup, cancellation check, and success emit choreography.

M4 should preserve output artifact ownership and treat native/FDK finalization convergence as in-scope.

Status-runtime finding

Rust emits EventStage, ProgressEvent, and QueueEvent; frontend StatusPanelRuntime tracks merge, batch, and metadata-save work kinds.

This supports M5 as a formal audit gate. It does not yet justify a status runtime implementation milestone by default.

The mandatory guard is narrower: preserve or explicitly improve the path from backend terminal event emission to command-result reconciliation to job-registry terminalization.

Handoff implication: the implementation agent should validate the public strip, track progress/cancel/finalization surprises in implementation notes, and expand M5 only with source evidence.

Candidate public strip shape

Inputs from processing

  • validated execution context/session
  • planned media inputs
  • encoder/toolchain settings
  • metadata outcome/write facts
  • output/staging intent
  • cancellation/progress handles

Outputs to processing

  • staged artifact candidate or execution result
  • media-integrity facts
  • adapter/toolchain facts
  • structured failure/cancel facts

Private cluster

  • adapter selection and FFmpeg/FDK routing
  • frame pipeline and stream probing
  • sample-buffer and encoder helpers
  • external process choreography
  • temp media staging mechanics

  • 3 Public strip candidate is named. Inputs, outputs, private helpers, and forbidden reach-throughs are clear enough to validate.

  • 5 Scout outputs are known. The implementation agent knows what to trace before making code moves.

Handoff shape

The implementation agent should be asked to validate the spec first, create an implementation plan, work it as an active goal on a fresh branch from main, and maintain a running implementation notes artifact.

The notes artifact should capture decisions not in the spec, changed assumptions, tradeoffs, deferred follow-ups, and anything the roadmap owner should know before PR review.

Status runtime and scout acceptance belong together: the implementation agent should track whether terminal event emission, command-result reconciliation, or job-registry terminalization requires status work, then keep, trim, or promote M5 based on evidence.

Accepted defaults: allow Rust visibility narrowing when it removes accidental public surface, preserve the existing progress/queue event contract unless audio correctness forces a change, and prefer one coherent PR unless implementation planning finds a concrete split reason.
