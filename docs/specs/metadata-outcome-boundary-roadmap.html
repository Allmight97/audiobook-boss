Metadata Outcome Boundary Roadmap

A forest-level architecture plan for making ABB metadata durable enough that future agents can change metadata behavior without rediscovering the same ownership traps.

Focus: Metadata All Layers In Scope Planning Thread Only One Roadmap PR Preferred

Destination

Metadata may flow through every gross layer, but metadata policy should not live in every gross layer. The rest of the app should ask the metadata boundary focused questions: what intent was expressed, what effective metadata should a job use, what metadata is safe for naming, and what write plan should be committed.

Operating Model

  • This thread: architecture/design alignment, roadmap shape, behavior decisions, and implementation-agent handoff prompt.
  • Not this thread: implementation work or continuous tests/checks.
  • Implementation: fresh Codex thread creates its own plan and works it as a goal.
  • Review: JStar plus two GitHub PR review agents; process should serve clarity, not ceremony.

Problem Statement

Metadata policy is still partly represented as call choreography: callers must know when to read source metadata, apply patches, sanitize for naming, preserve or clear cover art, write tags, and hand off to output or processing.

The target is not fewer files by itself. The target is less caller knowledge and a deeper metadata outcome boundary.

Metadata Forms

Metadata Intent Patch
Owner: TS helpers + Rust contract

Effective Metadata
Owner: Rust metadata boundary
Source metadata hydrated and patched for processing.
Naming Metadata
Owner: Rust metadata boundary
Sanitized metadata safe for output path generation.

Owner: Rust metadata boundary

Artifact Metadata
Owner: disk/backend readback truth
What actually exists in the final file after write or processing.

Code-Backed Flow Trace

Frontend Draft / Intent

  • metadataIntent.ts owns set, clear, noop, recompute, date normalization, and generated payload compilation.
  • metadataDraft.ts narrows ordinary UI drafts to writable form fields.
  • metadataState.ts stores current per-file metadata plus pending intent patches.

Workflow / IPC

  • metadataSaveWorkflow.ts sends pending intent requests to batch save.
  • processingWorkflow.ts stages dirty edits and passes metadata intent through output review and processing.
  • commands.ts compiles TS intent maps before generated Rust calls.

Backend / Artifact

  • intent_plan.rs resolves effective metadata and naming metadata.
  • processing/plan.rs currently choreographs read, patch, naming, cover policy, and output plan calls.
  • output_artifact/naming.rs renders paths but must trust callers to supply naming-safe metadata.

Accepted Posture

  • Primary focus: metadata before generic frontend glue.
  • Optimization: durable agent/human maintainability.
  • Scope: frontend, backend, and cross-layer metadata flow.
  • Roadmap: one active spec keeps planning and later implementation honest.
  • Glue rule: keep only real technical or ownership boundaries.
  • Branch: dedicated roadmap/metadata-outcome-boundary branch.
  • PR shape: default to one full-roadmap PR; split only for a concrete technical reason.
  • Review reality: optimize for JStar plus two GH review agents, not ceremony.
  • Behavior: mutable when necessary, but only after full metadata-flow tracing.

Behavior Definition

In this roadmap, behavior means what ABB does and produces at the product boundary: visible UX state, command outcomes, saved metadata, output paths, final files, tags, cover art, progress/terminal status, and error handling. Internal implementation shape is not behavior unless it changes an observable outcome or public contract.

Behavior stability is the default, not a prohibition. Behavior changes are allowed when they improve the metadata outcome boundary and have been traced through metadata forms, gross layers, public contracts, artifact truth, UX consequences, and compatibility impact.

Open Alignment Questions

QuestionRecommended default
How aggressive should naming/type changes be in MB1? Rename where it changes ownership or prevents misuse; avoid cosmetic churn.
How much temporary duplication is acceptable? Accept short-lived duplication only when it preserves behavior while moving ownership.
Which metadata behavior family should be traced first? Start with output naming because it crosses preview, preflight, hydration, legacy series-part sanitization, and artifact planning.

Implementation Handoff

Start a fresh implementation thread on roadmap/metadata-outcome-boundary. Read the roadmap source plus root and nearest nested AGENTS.md files. Use audiobook-metadata, contract-guardrails, and abb-library-research. Pre-validate the compact Rust metadata outcome plan before editing, then implement MB1-MB5 as one coherent PR unless review or rollback risk gives a concrete reason to split.

  • First move: design the metadata planning result consumed by processing and output planning.
  • Primary invariant: preserve explicit set | clear | noop intent and validation-before-read ordering.
  • Stop rule: route back to JStar before any deliberate behavior mutation not covered by the roadmap gate.
  • Final proof: defer broad checks until PR readiness; then use focused contract tests, public-strip checks, and scripts/checks.sh standard before runtime readiness claims.
