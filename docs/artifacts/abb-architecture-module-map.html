How To Read The Design

Boundary

A place where data or control crosses layers and must be normalized, validated, and kept contract-correct. In ABB, the most visible boundary is src/lib/tauri/client.ts wrapping generated Tauri bindings.

Seam

A deliberate join where a feature can change one side without making callers learn private implementation details. The generated binding seam exists for drift detection; the human-owned runtime seam is tauriClient.

Shim

A narrow adapter around outside behavior. ABB shims FFmpeg, mp4ameta, Tauri plugins, and external FFmpeg/FDK so product rules stay in owned modules instead of leaking library quirks upward.

Compiler And Build Chain, Grounded In ABB

The practical model: Bun runs scripts; TypeScript checks frontend types; Svelte and Vite compile the web UI; Cargo/rustc compile the Rust/Tauri backend; Tauri packages both into the macOS desktop app; Specta exports the Rust IPC contract back into TypeScript.

Feature Planning Heuristic

When thinking about a new feature

  • Name the product outcome first: import, inspect, decide, preflight, process, or verify.
  • Find the truth owner: UI state, runtime boundary, backend lifecycle, metadata intent, output artifact, or status runtime.
  • Change the private cluster when possible; change the public strip only when callers really need a new concept.
  • Use generated bindings as proof of contract alignment, not as the hand-authored API you design against.

Common layout implications

  • Import and metadata controls gather intent, but should not invent durable truth.
  • Preflight screens should show backend-owned output and collision plans.
  • Status and queue UI should render terminal truth from backend events/results.
  • Codec/tag details belong behind audio and metadata shims unless the user must choose a real product policy.
