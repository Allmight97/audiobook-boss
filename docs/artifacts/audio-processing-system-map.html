Conclusion first

Audiobook Boss turns intent into artifact truth.

The audio pipeline is a chain of boundaries: user intent in Svelte, normalized IPC payloads, backend preflight plans, job lifecycle, one of two processing engines, metadata shaping, destination-adjacent staging, final filesystem commit, progress events, and terminal result truth. The useful mental model is: Import -> Inspect -> Decide -> Preflight -> Process -> Verify.

Engine paths native ffmpeg-next and external FDK Encoder targets FDK, Apple AAC/AAC-AT, Native AAC Commit model stage beside destination, then move/install Fallbacks FB-010 and FB-012 removed on this branch UI truth generated Tauri contract via tauriClient

The Shape in One Screen

Think of ABB as a system that gradually removes ambiguity. Early layers are allowed to be tentative and user-shaped. Later layers must become concrete, validated, and observable.

1. Import User supplies audio paths by drag/drop or file picker. Cover art drops are routed separately.
2. Inspect Rust validates paths, probes audio, duration, codec, sample rate, channels, and decoder choice.
3. Decide UI state chooses encoder, toolchain, output directory, naming, metadata intent, and job type.
4. Preflight Backend builds the exact output plan, collision result, and review signature before writing.
5. Process Native ffmpeg-next or external FDK FFmpeg transcodes, tracks progress, handles cancellation.
6. Verify Terminal result reports what actually happened: success, skipped, cancelled, failed, or mixed.
SWE lesson: a good processing pipeline separates intent, plan, execution, and truth. When those collapse into one object, bugs hide in the overlap.

Glue, APIs, Seams, and Boundaries

Software systems stay navigable when each part has a clear job and a clear crossing point into the next part. In ABB, the useful question is: "What is the official way these two pieces are allowed to talk?"

API: the official crossing

An API is the contract one component exposes to another. It says what can be asked for, what shape the request must have, and what shape the answer will return. In ABB, tauriClient.processAudiobookFiles() is an internal frontend API over the generated Tauri command, while Rust functions like resolve_processor_adapter() are internal backend APIs.

Analogy: if modules are neighborhoods, an API is the official road between them. It makes movement possible without every caller walking through private kitchens, garages, and utility closets.

Boundary: the separation line

A boundary is the line between separate responsibilities. It can be between processes (Svelte and Rust), modules (metadata and audio), or even functions inside one module when one function owns validation and another owns side effects.

Seam: a useful change point

A seam is a boundary shaped so you can test, change, or swap one side without rewriting the other. ResolvedProcessorAdapter is a real seam: the run lifecycle can call one interface while native and FDK execution differ behind it.

Shim: a temporary bridge

A shim translates across a mismatch that should ideally disappear. Shims are useful when they unblock progress, but they need explicit ownership, trigger, and removal condition. FB-010 and FB-012 were removed because their purposes now live in stronger owned boundaries.

Glue: coordination code

Good glue is small, named, and boring: gather inputs, call the boundary, pass results onward. Bad glue is random cross-module knowledge with no contract. ABB's high-value glue surfaces are startProcessing(), tauriClient, backend run.rs, and ResolvedProcessorAdapter.

Study move: when a function feels confusing, ask which category it is: product logic, boundary adapter, orchestration glue, seam, shim, or artifact truth. That classification usually tells you what kind of tests and refactor pressure make sense.

Every Input That Feeds Audio Processing

"Audio processing input" is broader than audio files. The final artifact is shaped by file paths, metadata intent, encoder/toolchain selection, naming rules, collision policy, preview mode, concurrency, cancellation, and source inspection.

Audio paths

src/ui/fileImport/handlers.ts -> analyze_audio_files

  • Drag/drop and file picker collect candidate paths.
  • UI filters by supported audio extension before backend analysis.
  • Backend path validation canonicalizes and rejects unsupported or unsafe paths.
  • Inspection returns AudioFile plus stable DecoderSelection per file.

Metadata intent

src/ui/metadataState.ts and src/types/metadataIntent.ts

  • UI stores intent as set, clear, noop, and album-sort recompute operations.
  • Intent patches prevent confusing "field absent" with "user cleared field."
  • Processing resolves source metadata plus patch before naming and muxing.

Encoder settings

src/ui/encoderPanel/state.svelte.ts -> settings_encoder.rs

  • UI settings normalize into the boundary EncoderSettings.
  • Valid modes are constrained: FDK/Auto VBR, AAC-AT CVBR, Native AAC CBR.
  • Sample rate and channels can be automatic or explicit.
  • Thread settings are auto, off, or fixed.

External toolchain

src-tauri/src/audio/toolchain.rs

  • FDK requires a validated external FFmpeg binary with libfdk_aac.
  • User override path is tried first; valid auto-detection can rescue invalid override state.
  • Toolchain inspection also records available input decoders used by xHE-AAC handling.

Output directory and naming

src/ui/outputPanel/state.svelte.ts -> audio/output_path/*

  • Output directory is required before processing.
  • ABS default and custom template naming are rendered from effective metadata.
  • Preview output uses a .preview.m4b suffix.
  • Backend, not UI, owns final path truth and collision actions.

Job mode and review

src/ui/statusPanel/processing.ts -> audio_processing/plan.rs

  • Single/multi-file can merge into one output; batch produces one output per input.
  • Preview mode changes output kind and may clip input durations.
  • Collision review is captured by a preflight signature before execution.

Frontend: Where User Intent Becomes a Payload

The frontend does not own durable truth. Its job is to collect intent, normalize it into generated IPC shapes, ask Rust for authoritative plans, and render backend truth.

The main frontend route: startProcessing

src/ui/statusPanel/processing.ts is the frontend orchestration point. It reads output config, stages dirty metadata intent, computes full vs preview kind, asks for a backend preflight plan, handles collision review, starts listeners, and invokes tauriClient.processAudiobookFiles.

What this function gathers before process starts
  • Valid audio file paths from current file-list state.
  • Output config from output panel state: directory, encoder settings, toolchain settings, sample rate, naming.
  • Metadata intent map for merge or batch jobs.
  • Preview seconds when preview mode is requested.
  • Preflight review result, including collision policy and signature.

Status controller

src/ui/statusPanel/controller.ts owns the runtime listeners and state reconciliation. It starts and stops progress subscriptions, applies queue snapshots, requests cancellation, and reconciles the final process result into UI state.

Boundary adapter

src/lib/tauri/client.ts is the frontend contract seam. It converts UI shapes into generated Rust contract shapes, compiles metadata patches, denormalizes payloads, and wraps progress/queue event listeners.

File import

fileImport/handlers.ts routes audio drops to analyzeAudioFiles, appends validated file-list results, and keeps cover-art drops separate from audio import.

Encoder UI state

encoderPanel/state.svelte.ts is UI-owned state; toBoundaryEncoderSettings turns that state into the backend contract. This keeps display choices from leaking as fuzzy backend instructions.

Output UI state

outputPanel/state.svelte.ts owns selected output directory, naming config, preview text, estimated size, sample-rate display, and the final OutputConfig passed into processing.

Correct term: in ABB docs this is usually a boundary adapter or orchestration surface, depending on the layer. The UI status panel orchestrates the frontend workflow. tauriClient is the IPC boundary adapter. Rust command modules orchestrate backend lifecycle.

IPC Contract: The Narrow Waist

The IPC boundary is the narrow waist of the system. It lets the UI remain expressive while forcing backend execution to receive explicit, typed, generated shapes.

Command or event Purpose Why it matters
analyze_audio_files Validate and inspect selected audio files. Creates file-list truth, including duration and selected decoder identity.
validate_encoder_settings, list_available_encoders, refresh_external_toolchain Validate encoder mode and discover available encoders/toolchains. Keeps the UI honest about FDK, AAC-AT, and native AAC availability.
preview_output_path Ask backend how naming resolves. Prevents the UI from pretending it knows final path rules.
preflight_processing_plan Build exact output plan without writing. Produces collision actions and signature used to prove review did not go stale.
process_audiobook_files Run the selected processing jobs. Execution starts only after validation, planning, and optional review.
cancel_processing Request cancellation for active work. Sets registry cancellation flags; processors check them at critical boundaries.
processing-progress, processing-queue Return progress, queue, terminal stages, job IDs, and input indices. UI state follows backend truth instead of guessing from promises alone.

Preflight: Planning Before Side Effects

Preflight is where the backend turns "I want an output" into "this exact path will be written, skipped, renamed, blocked, or replaced." This is the data-loss safety layer.

What the plan computes

  • Merge vs batch job shape.
  • Final vs preview output kind.
  • Requested and resolved output paths.
  • Collision details and planned action.
  • Plan signature tied to reviewed outputs.
  • Effective naming metadata per input.

What it defends against

  • Existing files at the destination.
  • Two batch outputs claiming the same path.
  • Case-insensitive filesystem conflicts.
  • Output path overlapping an input source path.
  • Review going stale between UI confirmation and execution.
Collision policy in plain English
Policy/actionMeaningBehavioral point
FailDo not proceed if occupied.Good default for safety.
ReplaceExistingReplace destination when allowed.For batch-like collisions, ABB may choose rename instead of replace.
RenameNewCreate a non-conflicting candidate.Used when keeping existing files matters.
SkipExistingDo not run work for that occupied output.Batch can return skipped entries without starting encode work.
ReviewRequiredStop for user review.Hard blocks and unreviewed collisions cannot silently write.

Processing Engines and Encoder Targets

ABB has one lifecycle, two execution engine paths, and three encoder targets. The shared lifecycle is prepare -> execute -> finalize. FDK uses the external FFmpeg engine path; Apple AAC/AAC-AT and Native AAC use the in-process ffmpeg-next engine path.

Encoder targetBackend enum/nameExecution engine pathImportant setting mode
FDK HE-AAC EncoderType::FdkHeAac / libfdk_aac External FFmpeg process via external_fdk.rs VBR quality plus afterburner
Apple AAC / AAC-AT EncoderType::AacAt / aac_at Native ffmpeg-next process path via engine.rs CVBR
Native FFmpeg AAC EncoderType::NativeAac / aac Native ffmpeg-next process path via engine.rs CBR bitrate
Why Apple AAC is not a third engine: Apple AAC is a resolved encoder target inside the native ffmpeg-next execution path. The engine path is about how ABB runs the work; the encoder target is about which AAC encoder that path opens.

Native path: in-process ffmpeg-next

processor/engine.rs initializes ffmpeg-next, opens decoders, creates the output context, configures the encoder, loops packets and frames, resamples when needed, accumulates exact encoder-sized frames, writes packets, drains, and writes the trailer. This path covers both Apple AAC/AAC-AT and Native FFmpeg AAC. 

process_audiobook_with_context
  -> prepare::validate_and_prepare
  -> execute::execute_processing
  -> engine::FfmpegNextProcessor::execute
     -> setup_encoder
     -> setup_decoder_and_resampler for each file
     -> process_input_packets
     -> SampleAccumulator exact frame packing
     -> encode_and_write_frame
     -> finalize_encoding
  -> finalize::finalize_processing

Frame-size truth

SampleAccumulator supports F32 planar for Native FFmpeg AAC and I16 packed for Apple AAC/AAC-AT. The current branch removed the old FB-010 "guess frame size" behavior: EncoderFramePlan now owns frame-size fallback for known AAC encoders, and unresolved Auto reaching this layer is an invariant violation.

Preview behavior

Single-file preview stops once emitted PTS reaches requested seconds. Multi-file preview can take excerpts from each input and record preview chapter markers so the preview represents the run shape rather than only the first file.

Progress behavior

The frame pipeline emits converting progress roughly every second, based on processed media time relative to total planned duration, and includes current-file labels where available.

FDK path: external FFmpeg process

processor/external_fdk.rs runs the validated external FFmpeg binary when the resolved encoder is FDK. It builds a command, monitors -progress pipe:1, kills the child on cancellation, validates success, optionally rewrites metadata, then enters the same final commit boundary as native. 

ffmpeg
  -y -hide_banner -loglevel error -nostats -progress pipe:1
  [-t previewSeconds] [-c:a selected_input_decoder] -i input1
  ...repeat inputs...
  -map_metadata -1 -map_chapters -1 -vn
  [-filter_complex concat=...] OR [-map 0:a:0]
  -c:a libfdk_aac -profile:a aac_he
  -vbr <level>
  -afterburner 1|0
  [-ac channels] [-ar sample_rate] [-threads n]
  staging/temp-output.m4b

Input decoder contract

File analysis records stable decoder IDs. If a source needs a named decoder such as aac_at or libfdk_aac, external FDK validates that the chosen external FFmpeg exposes that decoder before execution.

Metadata on FDK path

External FFmpeg handles the audio encode. ABB then rewrites or merges metadata when effective metadata or passthrough cover/chapters require it, while preview output keeps cover art but not full chapter passthrough.

External progress

ABB parses out_time_ms, out_time_us, and out_time lines from FFmpeg progress output and updates the same UI progress channel used by native processing.

Prepare

prepare.rs revalidates inputs, validates output paths and sample-rate config, detects target sample rate when automatic, computes total duration, and creates a destination-adjacent staging directory.

Execute

Native and FDK both write into a temporary output inside the staging directory. This keeps partial artifacts away from the final destination path.

Finalize

finalize.rs commits the temp output to the final artifact path, handles metadata finalization when needed, cleans staging artifacts, emits complete progress, and reports final truth.

Metadata: Intent, Source Truth, and Muxing

Metadata is a parallel pipeline that feeds naming and final muxing. The important rule: metadata patches are not complete metadata objects. They describe user intent over source truth.

Effective metadata resolution

resolve_effective_processing_metadata reads source metadata when needed, applies the metadata intent patch, and returns effective metadata for output naming and processor execution. This prevents partial edits from dropping untouched title, author, series, cover art, or publication date.

Reader routing

metadata/reader.rs prefers the mp4ameta bridge for MP4-family containers, then normalizes cover art. Other containers use ffmpeg metadata reads.

Passthrough

metadata/passthrough.rs extracts cover art and chapters. For multi-file merges, ABB can synthesize chapters from file order and duration when no source chapters exist.

FFmpeg dictionary

metadata/ffmpeg_dict.rs maps ABB metadata to container keys, including artist and album_artist, series plus iTunes mirrors, sort album, media type, date/year, comment, and description.

Footgun to remember: a patch map is a delta, not the whole book record. Treating it as complete metadata causes classic "Unknown Author" or "Untitled" output naming bugs.

Output and Filesystem Mechanics

ABB uses host filesystem mechanics to keep partial work separate from the final artifact and to avoid corrupting or deleting existing outputs when the destination refuses a write.

Destination-adjacent staging

processor/staging.rs creates .abb-processing-<uuid> beside the final artifact. This reduces cross-volume rename problems and makes cleanup mechanically local to the destination.

Cleanup guard

cleanup/guard.rs tracks temp dirs and outputs. On success, committed paths are removed from cleanup tracking. On failure/cancel/drop, tracked temp artifacts are removed where possible.

Commit boundary

finalize.rs owns the final move/install. This is the boundary where a successful temp artifact becomes a user-visible output.

FB-012 is gone

ABB no longer has a copy-replace fallback after failed replace rename. If replace fails, the operation fails clearly instead of trying a second, riskier replacement strategy.

What happens for write, rename, replace, and skip
  • Write/RenameNew: ABB installs without replacing. It prefers hard-link-plus-remove, then create-new copy if needed, and refuses if the destination changed.
  • ReplaceExisting: ABB uses filesystem rename to replace the final path. If that fails, it reports failure. No copy-replace fallback.
  • SkipExisting: execution for that output is skipped and a terminal skipped result is returned.
  • ReviewRequired: execution is blocked until the user reviews and submits a matching preflight signature.

Encoder and FDK Toolchain Selection

Encoder choice starts as UI preference but becomes backend truth only after availability and settings validation.

Resolution priority

  1. FDK if a valid external FFmpeg with libfdk_aac is available.
  2. Apple AAC/AAC-AT on macOS when ffmpeg exposes aac_at.
  3. Native AAC when ffmpeg exposes aac.

resolve_encoder_type() owns this decision. Unresolved Auto should not reach encoder open.

How UI settings are honored

  • FDK/Auto require VBR quality; external args use -vbr and -afterburner.
  • Apple AAC/AAC-AT requires constrained VBR and uses I16 packed samples.
  • Native AAC requires CBR bitrate and uses F32 planar samples.
  • Explicit sample rate maps to -ar externally or encoder rate internally.
  • Explicit channels map to -ac externally or encoder layout internally.
  • Thread settings map to external -threads or native encoder thread options where supported.
FDK path detection details

toolchain.rs checks a user override first, then auto-detected candidates: Homebrew FFmpeg prefix, pkg-config linked FFmpeg, which ffmpeg, /opt/homebrew/opt/ffmpeg/bin/ffmpeg, and /opt/homebrew/bin/ffmpeg. Candidate validation checks the binary exists, is acceptable for Apple Silicon expectations, can run ffmpeg -version, exposes libfdk_aac in -encoders, and records available decoders.

Feedback Loops

A feedback loop is any path where backend truth changes frontend state. ABB has three main loops: progress events, queue snapshots, and final command results.

Progress loop

ProgressEmitter emits analyzing, converting, writing metadata, cleanup, completed, failed, cancelled, and skipped events through processing-progress.

Queue loop

Batch jobs emit queue state with job IDs and input indices so the UI can show parallel work without losing per-file terminal outcomes.

Result loop

ProcessCommandResult summarizes success, skipped, cancelled, failed, or mixed outcomes. The UI reconciles this after the process command returns.

Cancellation loop

UI calls cancel_processing. The registry sets global or per-job flags. Native loops and external process monitors check flags and terminate cleanly.

Failure Semantics and Footguns

The current shape is intentionally stricter after the FB-010 and FB-012 refactor. Failing loudly at the owning boundary is preferred over hidden fallback behavior that can mutate artifacts in surprising ways.

Situation Current behavior Why it is shaped that way
Encoder reports frame size 0 Known AAC encoders use EncoderFramePlan AAC quantum handling; unresolved Auto is an error. Frame-size policy belongs near encoder resolution, not inside sample-buffer fallback code.
Replace commit rename fails ABB returns a clear failure; it does not copy-replace as a fallback. Copy-replace after failed replace can be brittle on network/share filesystems and risks partial truth.
Network/share destination refuses final commit The staged artifact may remain cleanup-eligible; the existing output should not be deleted or corrupted. ABB cannot make the host filesystem reliable, but it can avoid making the failure worse.
Cancellation after final move Finalize checks cancellation after move, but output already committed can still be reported as success with warning semantics. Once the artifact exists at the final path, lying that it did not succeed creates worse terminal truth.
One batch item fails Scheduler continues other tasks and returns deterministic per-index results. Batch UX needs complete outcome truth, not first-error blindness.

Glossary for Studying the System

These are the terms that make ABB easier to reason about without drowning in file names.

TermMeaning in ABBWhy it helps
APIThe official contract one component exposes to another: what can be called, what request shape is allowed, and what result shape returns.It is the road across a boundary, not the whole neighborhood.
BoundaryThe responsibility line between separate code worlds, such as UI/Rust, command/processor, metadata/audio, or plan/execute.Finding the boundary tells you where translation and validation should happen.
Boundary adapterA layer that translates between two worlds, such as UI state and generated Tauri types.It should normalize, not invent business truth.
GlueCoordination code that gathers data from several owners and calls the next boundary.Good glue is explicit and boring; bad glue smuggles cross-layer rules everywhere.
Orchestration surfaceA function/module that sequences work across several owners, like startProcessing or backend run dispatch.It coordinates but should not hide every rule inline.
Artifact truthThe real final file and result after processing completes.Playback feelings are useful, but artifact truth is objective.
Terminal truthThe final status for each job: success, skipped, cancelled, failed, or mixed.Prevents UI from hanging or claiming success from partial evidence.
Intent patchUser metadata changes expressed as set/clear/noop operations.Preserves the difference between untouched and intentionally cleared fields.
FallbackA deliberate alternate behavior with trigger, marker, and removal condition.ABB policy avoids silent convenience fallbacks because they rot into hidden product behavior.
ShimA compatibility translation layer that hides a mismatch.Useful only when the mismatch is real and explicitly owned.
SeamA boundary where behavior can be tested or replaced independently.Good seams reduce future refactor pain; false seams just add indirection.
