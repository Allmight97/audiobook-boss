What the contrast actually says

The boxes did not move. The questions they answer did. On main, four "leaks" were the day-to-day cost:

1. Two files, one rule

Hard-block collision logic lived in backend collision-kind names and in the frontend review file. Either side could change and silently drift.

2. Sideways imports

The planner reached into the processing-command file for metadata projection; the processor reached into filesystem commit; the UI reached into status view state. Each one is fine alone, together they make the dependency graph dense.

3. Public/private mixed in one file

client.ts on main is 350 LOC of public surface plus private generated-binding glue. There is no file you can point at and say "this is the public API".

4. One module absorbs everything nearby

run.rs on main was 1026 LOC because it accreted metadata helpers, input shape, plan assembly, review, parent-dir creation, and dispatch all in one place.

What changed most?

The architecture is now product-decision-first. Files still live in Rust and Svelte lanes, but ownership is expressed through grey-box APIs.

What stayed stable?

Command names, event names, user workflows, metadata intent semantics, and output behavior are intended to remain equivalent to main.

What is still provisional?

Full replacement readiness waits on manual parity. This branch is ready for testing, not declared done.

Single MP4 file: what happens to it, old vs new

Imagine one file: ~/Books/big-book.mp4. The user drops it in, edits a couple of tags, picks an output folder, hits Process. Both architectures end up with the same audiobook file in the same place. The difference is who answers which question along the way. Numbered steps line up so you can read them side by side. orange = the same product moment

Main (today's release branch) old shape

  1. UI picks the file
    The user drops big-book.mp4 into the file list. The frontend holds an array of paths and a draft MetadataIntentPatch.
  2. tauriClient.analyzeAudioFiles([path])
    src/lib/tauri/client.ts is one 350-line file that mixes the public tauriClient, the private commandSpecs, the generated-binding adapter, and result normalization in one place.
  3. Backend reads MP4 facts
    Rust uses FFmpeg + the mp4ameta bridge to return duration, codec, sample rate, channels, and a tag snapshot. The UI fills the metadata form.
  4. User edits metadata, picks output folder
    Title, author, year. Output folder is ~/Audiobooks/. Encoder is Native AAC. Naming preset is the default.
  5. Preflight builds the plan (preview)
    run.rs::preflight assembles ProcessingInputs, calls plan.rs::build_processing_plan, which reaches back into run.rs::resolve_effective_processing_metadata and run.rs::resolve_naming_metadata (metadata projection lives inside the processing-command file). The plan is returned to the UI.
  6. Frontend decides hard-block on its own
    outputPlanReview.ts looks at collision.kind and re-derives whether source/destination overlap or canonical path overlap means "you can't proceed". The collision semantics live in two places: backend collision detector and the frontend re-derivation.
  7. Collision dialog (if needed)
    User picks Overwrite / Skip / Keep / Rename / Cancel. Frontend re-calls preflight with the chosen collisionPolicy and stores the returned planSignature.
  8. Process command starts
    run.rs::execute assembles ProcessingInputs again, calls build_processing_plan again, then log_output_plan, enforce_plan_review, and ensure_output_parent_dirs inline. Each one is a separate concept run.rs has to know about.
  9. Job registers, processor runs
    JobRegistry gives an id and a permit. The processor adapter decodes, resamples, encodes, and muxes into a temp file.
  10. Processor owns the final move
    processor/finalize.rs (548 LOC) owns commit policy: commit_output_boundary → move_to_final_location (hard-link, copy, or rename). The processor module decides filesystem truth, not the output module.
  11. Status panel: external view-state poke
    jobControls.ts imports setStatusPanelConcurrencyText directly from statusPanel/viewState.svelte.ts. The panel's view state is reachable from outside the cluster.
  12. Done. UI shows success.
    Terminal event fires. Final big-book.m4b exists in ~/Audiobooks/<author>/<title>/.

Grey-box branch (this lab) new shape

  1. UI picks the file
    Same UI, same file, same draft patch. No frontend behavior change here.
  2. tauriClient.analyzeAudioFiles([path])
    client.ts is now 161 lines of just public surface. Generated invocation, payload translation, error mapping, and result normalization live in src/lib/tauri/commands.ts (200 LOC) and stay private behind the boundary.
  3. Backend reads MP4 facts
    Same FFmpeg + mp4ameta read path. Unchanged behavior; this lives in the metadata boundary already.
  4. User edits metadata, picks output folder
    Same fields, same intent. set | clear | noop intent is compiled at the Tauri boundary, not scattered across UI callsites.
  5. Preflight asks the planner one question
    run.rs::preflight calls plan.rs::resolve_preflight_plan. The planner itself asks metadata::resolve_effective_processing_metadata and metadata::resolve_naming_metadata (now in metadata/intent_plan.rs). Metadata projection lives in the metadata boundary, not in the processing command file.
  6. Frontend reads backend-authored review
    outputPlanReview.ts checks output.review?.canProceed === false and shows output.review?.message. Hard-block policy is owned by audio/output_path/review.rs. The UI renders truth instead of re-deriving it.
  7. Collision dialog (if needed)
    Same UX. User picks a policy; the frontend re-asks preflight and stores the new planSignature.
  8. Process command starts
    run.rs::execute calls plan.rs::prepare_execution_plan — one function. Inside, the planner rebuilds, asks output_path/review.rs::enforce_output_plan_review, and ensure_output_parent_dirs from the same module. The orchestrator no longer knows which sub-step lives where.
  9. Job registers, processor runs
    Same JobRegistry, same processor adapter, same temp output.
  10. Output module owns the final move
    processor/finalize.rs shrank to 101 LOC and delegates to output_path/commit.rs::commit_output_artifact. Filesystem truth now belongs to the output module — not the processor.
  11. Status panel: tiny boundary API
    jobControls.ts calls updateStatusPanelConcurrencyStatus(message) from statusPanel/runtimeApi.ts. The view-state file is no longer reachable from outside.
  12. Done. UI shows success.
    Same terminal event. Same final big-book.m4b in the same place. User cannot tell the architecture changed — on purpose.

What the trace teaches

Step 5: who owns metadata projection

On main, the planner reaches back into the processing-command file to do metadata math. In grey-box, the planner asks the metadata module. The metadata module owns the answer to "what becomes the title for naming and tag-writing".

Step 6: who owns "can proceed"

On main, the frontend re-derives hard-block kinds. In grey-box, the frontend reads output.review.canProceed. One owner (backend) authors the rule; the UI renders it. This is the single biggest "duplicate policy" reduction.

Step 10: who owns the file move

On main, the processor owns commit (hard-link, copy, rename). In grey-box, the output module does. The processor finalize file dropped from 548 to 101 lines because it no longer carries policy that does not belong to it.

"Same outcome, different ownership" is the whole point

User-visible behavior is unchanged on purpose: same commands, same events, same final file, same metadata. The architecture refactor is invisible to the user and extremely visible to anyone (human or agent) trying to change one rule without stepping on three others. That is the grey-box promise: a small, owned public API wraps a private implementation that any contributor can replace as long as the promise holds.

Concrete ownership diffs (the real spaghetti receipts)

These are not invented examples. Each card cites real files on both branches. The "old" side is from /Users/jstar/Projects/audiobook-boss on main; the "new" side is this lab worktree on arch/grey-box-modules. Sizes and quoted code are from the actual files.

1. Who decides "this output collision is a hard block"?

The clearest case of duplicate policy across the IPC boundary. Same product decision, two implementations.

Main — UI re-derives the rule

src/ui/statusPanel/outputPlanReview.ts

function getHardBlockingCollisionMessage(plan) { const blocked = plan.outputs.find( (output) => output.collision?.kind === 'source_destination_overlap' || output.collision?.kind === 'canonical_path_overlap', ); // ... }

The frontend has to know which collision kinds are hard blocks. If the backend ever adds a new hard-block kind, this list drifts silently.

Grey-box — UI reads backend truth

src/ui/statusPanel/outputPlanReview.ts

function getBlockingReviewMessage(plan) { const blocked = plan.outputs.find( (output) => output.review?.canProceed === false, ); return blocked?.review?.message ?? null; }

The backend authors review.canProceed and review.message in audio/output_path/review.rs. The UI renders that fact. Adding a new hard-block kind in Rust now reaches the UI for free.

2. Who commits the final audiobook file?

The processor module used to own filesystem commit behavior, sandwiched between encoding and cleanup. That put filesystem policy inside the audio engine.

Main — processor owns commit

src-tauri/src/audio/processor/finalize.rs — 548 LOC

pub(crate) fn move_to_final_location( temp_output: PathBuf, final_path: &Path, action: PlannedOutputAction, ) -> Result<PathBuf> { /* hard-link / copy / rename */ } pub(crate) fn commit_output_boundary( context, temp_output, destination, cleanup_guard, ) -> Result<FinalizeCommitOutcome> { ... }

The processor mixes encoder policy with filesystem policy. Anyone changing commit behavior has to touch the audio engine module.

Grey-box — output module owns commit

src-tauri/src/audio/processor/finalize.rs — 101 LOC (just delegates)
src-tauri/src/audio/output_path/commit.rs — 448 LOC (owns commit)

// finalize.rs now just asks the output boundary: let outcome = commit_output_artifact( context, merged_output, destination, cleanup_guard, )?;

Filesystem commit, hard-link/copy/rename strategy, and reviewed-signature enforcement all live in the output module. The audio engine is back to being about audio.

6. What run.rs::execute has to know

The most visible "the orchestrator no longer juggles 5 helpers" moment. Both snippets are the heart of the process command.

Main

let inputs = ProcessingInputs { output_naming: payload.output_naming.clone().unwrap_or_default(), base_output_dir: resolve_output_dir(&payload.output_dir, true)?, preview_seconds: resolve_preview_seconds(preview_seconds), }; let plan = build_processing_plan(&payload, metadata.as_ref(), &inputs)?; log_output_plan("process", &payload, &plan); enforce_plan_review(&payload, &plan)?; ensure_output_parent_dirs(&plan)?; match plan.job_type { /* dispatch */ }

Five separate concepts run.rs has to know about before it can dispatch.

One question to the planner, then dispatch. The planner internally owns input shape, review, and parent-dir creation. The orchestrator owns orchestration.

What this map of diffs adds up to

None of these changes shift user-visible behavior. They move the answer to a product question into the module whose name matches that question. The two side effects matter most:

  • One owner per rule. Reviewing or changing a rule now means opening one file by name, not chasing it across modules.
  • Public APIs document intent. Names like resolve_preflight_plan, commit_output_artifact, resolve_effective_processing_metadata, and updateStatusPanelConcurrencyStatus describe what the caller wants, not how the callee does it.

1. APIs name product decisions, not helper categories

The public surfaces are shaped around questions ABB actually asks: what work is safe, what metadata intent means, where the artifact goes, what IPC the UI may call, and what runtime status the user should see.

semantic boundary agent-navigable

2. Artifact truth is backend-authored end to end

The output boundary produces review truth and commit policy. The UI renders that truth and collects the user's choice; it no longer reverse-engineers collision semantics from lower-level path facts.

less duplicate policy safer preview-to-run path

3. Metadata intent stays explicit until a boundary projects it

set, clear, and noop are preserved as intent. Processing metadata and naming metadata are derived views, which reduces drift between save behavior, preview naming, and final output.

intent before projection clear/noop tests

4. Generated contracts are used behind one runtime adapter

Specta-generated bindings still protect TS/Rust parity, but regular UI code calls tauriClient. That makes generated shape changes cheaper because the blast radius is the Tauri boundary, not the whole frontend.

contract parity remains guard blocks leaks

5. Status exports behavior, not internal state ownership

Other UI code can ask the status panel runtime to update user-visible status, but it does not own the reducer, controller, feedback model, or view-state derivation.

narrow UI API private runtime cluster

6. Tests should lock behavior at the API strip

The useful test target is the public promise: resolved plans, review requirements, metadata projections, IPC normalization, and status behavior. Private helpers can move as long as those promises hold.

grey-box module contract manual parity still required

Two Repo-Organization Suggestions

1

Make each grey-box API strip visually obvious in the tree

Keep public entry files small and boring: Rust mod.rs or named API files, TS index.ts or runtimeApi.ts. Put private implementation files beside or below them, and have callers import only the strip.

2

Add scoped boundary guidance only where rules differ

Keep root guidance broad. Add nested AGENTS.md files only for boundaries with special invariants, such as Tauri IPC, metadata intent, output artifact planning, or processing orchestration.

What To Notice During Manual Testing

  • If preview and final processing disagree, suspect an API contract between planning and commit.
  • If metadata save, naming, and output tags disagree, suspect metadata intent projection.
  • If the UI seems to know a backend rule, ask whether the backend should return a more user-ready fact.
  • If a status message feels wrong, ask whether status runtime is displaying terminal truth or a local guess.

Caller Smell Test

  • Healthy caller: passes user intent, receives a domain answer, and does not duplicate policy.
  • Suspicious caller: imports private files, interprets raw enums, or recomputes another module's rule.
  • Healthy API: caller can ask one clear question without knowing the module's internal workflow.
  • Suspicious API: caller must pass many unrelated parameters or assemble hidden preconditions by hand.

Reading code without writing code

You can navigate ABB confidently as a non-coder by reading four things in order: the file name, the import block, the public function signature, and the first paragraph of the body. The rest is implementation detail you can ignore until you need it. 

1. File path tells you the owner
src-tauri/src/audio/output_path/review.rs
                ^^^^^^^^^^^^^^^^^^^^^^^^^^
                module: output artifact review

2. Imports tell you the neighborhood
use super::plan::ResolvedOutputPlan;
use super::types::{OutputCollisionKind, PlannedOutputAction};
use crate::errors::Result;
  // → this file works with output plans, collision kinds,
  //   and the project-wide error type.

3. The public function signature is the contract
pub(crate) fn enforce_output_plan_review(
    plan: &ResolvedOutputPlan,
    review: OutputPlanReview,
) -> Result<()>;
  // → "given a plan and a review intent, succeed if the move is allowed,
  //    fail with a typed error if it is not." That is the whole promise.

4. The body is the implementation, optional reading
{
    // signature check, collision rules, parent-dir validation...
}

If you can describe a function in one sentence after reading items 1–3, the module is doing its job. If you cannot, that is a real signal — either the name lies, or the function is doing too many things.

Auditing a Private Cluster's code shape

Once the public API of a grey-box module is locked, the next useful pass is a cluster audit: a non-mutating gut check of what is inside the cluster. You are not refactoring yet — you are deciding whether internal refactoring would buy enough clarity to be worth the diff. Use one module at a time. Read, mark candidates, move on.

File size

Target < 475 LOC per non-test file; cohesion review at ~350. Big file = candidate to split around internal steps, without changing the Public API Strip.

Function size

Prefer <= 70 LOC per function. Larger orchestrators are fine when they preserve boundary clarity. Document the exception inline; do not hide it.

Parameter count

More than 7 parameters on a public function → propose a typed config object. On a private helper → gut check; usually means the helper is doing two things.

One decision per function

If a function does plan + review + commit, that is three decisions. Split inside the cluster; do not change the public function that callers use.

No reach-throughs

The cluster should only import from itself, the project's shared error types, and other modules' Public API Strips. An import that reaches into another module's internals is a smell, not a shortcut.

Tests near the behavior

Tests that prove the Public API behavior belong in the contract test file. Tests that prove internal helper shape belong in the cluster itself. Internal tests can be deleted freely when a helper goes away.

Cluster audit is non-mutating by design: capture findings in a short note per module and let later, deliberate refactor passes act on them. The Public API Strip is the contract; internal moves are the safe edit zone.

Implementation Vocabulary For This Repo

Architecture says where truth belongs. Implementation is the code-level machinery that makes that map real: functions, methods, types, classes, modules, tests, state, events, and subsystems. You do not need to write this code to reason about whether the machinery is serving the system.

Function

A function is a named chunk of behavior. Callers pass inputs, the function does work, and it may return an answer. In ABB, functions are often the public API strip or a private step inside a grey-box module.

resolve_preflight_plan(payload, metadata, preview_seconds) -> returns a user-reviewable ProcessingPreflightPlan

Useful testing question: does this function answer one clear product question, or is the caller forced to know hidden steps?

Method

A method is a function attached to a type. In Rust, methods live inside an impl block. They are useful when behavior needs the type's stored state.

let mut ledger = OutputPlanLedger::new(); let output = ledger.resolve(path, kind, policy, source_paths);

In ABB, ledger.resolve(...) is a method because the ledger remembers claimed output paths while planning a batch.

Type

A type names the shape of data or the allowed choices. Types are how ABB tells code what a valid processing result, output plan, status, or review answer looks like.

type OutputPlanReviewResult = | { status: 'approved'; payload; plan } | { status: 'blocked'; message; plan } | { status: 'cancelled' };

In ABB, types help make impossible states harder to represent, like treating a cancelled review as though it were approved.

Class

A class is a template for an object that carries data and methods together. ABB uses this style in TypeScript where a runtime controller needs long-lived state and behavior. Rust usually expresses this idea with a struct plus methods in an impl block.

export class StatusPanelRuntime { public async startProcessing(...) { ... } public reconcileProcessResult(result) { ... } }

In ABB, StatusPanelRuntime holds status model state, progress listeners, cover art tracking, render timing, and methods that change the panel over time.

Module

A module is a code boundary: a file, folder, or Rust module that groups related behavior and decides what other code may import.

audio/output_path/ mod.rs exposes the public strip plan.rs, review.rs, commit.rs stay inside the cluster

In ABB, modules are how the grey-box architecture becomes visible in the repo tree.

Subsystem

A subsystem is a larger working area made of modules, files, functions, tests, and runtime behavior. It usually owns an end-to-end slice of the product.

Status Panel Runtime controller + reducer/model + events + rendering + services + tests

In ABB, the status panel is a subsystem. The grey-box API lets other code interact with it without owning its internals.

How These Pieces Fit Together

Functions and methods are moves

They perform a step: resolve a plan, commit an artifact, update status, normalize an error, or render output.

Types describe shape

They name allowed data and choices: PlannedOutput, CollisionPolicy, ProcessingStatus, or OutputPlanReviewResult.

Classes and structs hold state

They package state and behavior: OutputPlanLedger remembers claimed paths; StatusPanelRuntime remembers UI runtime state.

Modules and subsystems own truth

They decide where rules belong: output artifact truth, metadata intent, runtime IPC, processing plans, or status-panel truth.

The vocabulary you said felt overwhelming

These are the words that show up in every architecture conversation. Each card uses an ABB example, not a textbook one.

Caller

The code that uses something. jobControls.ts is the caller when it calls updateStatusPanelConcurrencyStatus(...).

Callee / owner

The code being asked. The status panel runtime is the callee here. It is also the owner of "what concurrency status feels like to the user".

Callsite

The exact line where the call happens. When someone says "fix the callsites", they mean every line that calls a thing whose contract just changed.

Public API

The set of functions, types, and events a module promises to keep stable. tauriClient, resolve_preflight_plan, and commit_output_artifact are all public APIs.

Interface

Same idea as public API. In TypeScript an interface is a named shape; more generally, an interface is "the contract you can rely on without opening the implementation".

Boundary

A line in the code where one ownership zone ends and another begins. ABB has a TS↔Rust boundary, a frontend↔backend boundary, and a public/private boundary inside each grey-box module.

Contract

The promise the owner makes to callers about behavior. "Given these inputs, you get this kind of answer, with these typed failures." Tests lock the contract.

Adapter

A translation layer. src/lib/tauri/commands.ts adapts the user-facing tauriClient calls to the generated Rust bindings, normalizing shapes in both directions.

Public / private

Public = other modules may call it. Private = internal helper. In Rust, pub vs no pub; in TS, exported vs not. Grey-box modules keep the private set large and the public set small.

Coupling

How much one module has to know about another. Tight coupling = changing one forces changes in many. Loose coupling = a change stays inside its owner.

Cohesion

How closely the pieces in a module belong together. A module with high cohesion answers one product question. Low cohesion = a grab bag.

Encapsulation

Hiding implementation behind an interface so callers cannot depend on it. Encapsulation is what makes the inside of a grey-box module safe to change.

Signature

The name + inputs + output type of a function. Reading the signature alone should tell you what the function promises.

Side effect

Something a function does besides returning a value: writes a file, emits an event, mutates state. Commit functions have side effects; planning functions aim not to.

Idempotent

Calling it twice has the same result as calling it once. Useful for retry-safe operations. Most planning code in ABB is idempotent on purpose.

Variant

One choice inside an enum or union. PlannedOutputAction has variants like Write, ReplaceExisting, ReviewRequired.

Other Implementation Words You Will See

Struct

Rust data shape with named fields. Example: PlannedOutput describes requested path, resolved path, collision, review, and action.

Enum / union

A closed list of variants. Example: Rust PlannedOutputAction and TS OutputPlanReviewResult both model allowed outcomes.

Interface

TS object contract. Example: OutputPlanReviewRequest names the payload, metadata intent, and optional preview seconds a caller must provide.

State

Data remembered over time. Example: StatusPanelRuntime holds the current status model and render timers.

Import / export

The doorway between modules. Exported items are callable from outside; private helpers stay inside the grey-box implementation cluster.

Async / promise

Work that finishes later. Example: frontend calls through tauriClient return promises while Rust processing continues in the backend.

Event

Runtime message emitted over time. Example: processing progress and queue events let the status panel update while jobs run.

Test

Executable expectation. In grey-box modules, tests should lock public behavior more than private helper shape.

Ousterhout-Style Flexibility

Small code units are useful only when they make the system simpler to understand. A deeper module may have more internal code if its public API is simple, stable, and hard to misuse.

  • Good large module: one clear public surface, private complexity, behavior tests.
  • Bad large module: unrelated responsibilities and callers that must know internals.
  • Good small function: names a real step and reduces caller burden.
  • Bad small function: hides simple logic behind extra jumping and fake seams.

ABB Design Judgment

The code-shape triggers are review prompts, not automatic laws. The better question is whether splitting preserves the grey-box contract or weakens it.

  • Split when a private step has its own invariant, tests, or vocabulary.
  • Keep together when splitting would expose private workflow as public API.
  • Accept a longer orchestrator when it reads like a clear sequence of product steps.
  • Document exceptions when size is serving boundary clarity.

Manual Testing Lens

You can guide this work without writing code. When something feels off, translate the feeling into one of these implementation questions.

Wrong behavior

Which public function or method promised this behavior, and what caller trusted it?

Confusing result

Is the API returning the right product concept, or leaking a raw implementation fact?

Hard to explain

Is this a module-boundary problem, a function-shape problem, or simply a missing term?

Frontend / Backend Mental Model

The frontend/backend split is still real at runtime, but it is not the main architecture story anymore. The main question is: which product decision owns this rule?

Old mental model

  • Find the frontend file.
  • Find the backend file.
  • Compare duplicate policy in each.
  • Hope glue and tests agree.

New mental model

  • Start at the public API strip.
  • Identify the product decision owner.
  • Trust behavior tests and guards first.
  • Open private internals only when needed.
Concrete example: collision review

The frontend no longer re-derives hard-block collision policy from collision kinds. It reads backend-authored output.review. That makes the output artifact boundary the owner of review truth, while the UI owns the dialog and user decision.

Concrete example: generated bindings

Generated bindings are still used, but runtime code now reaches them through the Tauri boundary. The guard blocks generated command/event invoker leaks outside the intended adapter files.

Old State Pressure

  • Planner and runner both knew too much about output path details.
  • Processor finalization owned final artifact filesystem policy.
  • Frontend output review duplicated backend collision semantics.
  • Metadata intent projection lived near command planning instead of metadata.
  • Runtime boundary mixed public tauriClient with generated command glue.
  • Job controls reached into status panel view state directly.

New State Ownership

  • Planning asks resolve_preflight_plan or prepare_execution_plan.
  • Output artifact boundary owns commit, collision review, and parent-dir policy.
  • Frontend renders backend-authored review truth.
  • Metadata boundary owns intent/write-plan and naming/processing projection.
  • tauriClient is public; commandSpecs and generated calls are private.
  • Status runtime API closes the external view-state leak.

Obsolete seam absorbed

commit_output_boundary and final move policy moved out of processor finalize.

Duplicate policy shrunk

UI hard-block review now reads output.review instead of duplicating collision kind logic.

Boundary guard added

Raw generated invoker access is guarded by scripts/check-no-bridge-imports.sh.

What to watch for during your remaining tests

These are the categories of bugs the grey-box refactor is most likely to have introduced, ranked by how likely each is and what it would look like.

1. Collision review behavior drift

The biggest semantic move: the UI now reads output.review.canProceed instead of re-deriving hard-block collision kinds. If a collision case fails to open the dialog (or opens it for the wrong reason), suspect audio/output_path/review.rs. Test Overwrite, Skip, and Keep Existing on a real temporary output to confirm each path commits the correct file.

2. Metadata projection edge cases

resolve_effective_processing_metadata and resolve_naming_metadata moved from audio_processing/run.rs to metadata/intent_plan.rs. If output filename, ID3/MP4 tags, or naming preset behavior disagrees with main, that's where to look. Most exposed: cleared dates, cleared covers, legacy series-part numbers.

3. Final commit policy on cross-volume output

commit_output_artifact moved out of processor/finalize.rs into audio/output_path/commit.rs. The hard-link → copy fallback logic was supposed to come along intact. Test by pointing the output to a folder on a different volume than your temp/scratch dir and verify a full encode still produces the correct file with no leftover temp.

4. External FDK toolchain validation

Encoder/toolchain validation still lives in run.rs but the plan builder runs first. If the user selects FDK with a missing or wrong external ffmpeg binary, preflight should fail with a clear error, not a cryptic late-stage crash. This is the most fragile cross-runtime contract.

5. Concurrency status text in the panel

jobControls now goes through runtimeApi for the "N of M jobs running" message instead of poking view state. If that text gets stuck stale, never updates, or never clears at end of batch, the new boundary is the first place to look.

6. Preflight signature drift between preview and run

On reviewed-collision flows the UI carries a planSignature back into the process call. If the backend says "stale signature" when the user clicks Process right after the dialog, suspect plan.rs::build_plan_signature producing a different string than the one the preview returned for the same inputs.
