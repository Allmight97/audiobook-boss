# Library Research

This skill streamlines accuracy checks by combining **documentation lookup** with **source inspection**.
Use it when auditing, planning, or implementing changes that rely on third‑party APIs.

## Core Principle

- **Docs are authoritative for API contracts.**
- **Source is authoritative for behavior and edge cases.**

If docs and source disagree, call out the conflict and prefer docs unless you have a confirmed version mismatch.

---

## Universal Usage (Tool‑Agnostic)

### Documentation Flow (2 steps)

1) **Resolve the canonical library ID** for the package.
2) **Query the documentation** with a focused question (one API or behavior at a time).

This pattern applies across harnesses even if tool names differ.

**Common aliases you may see:**
- Resolve step: `resolve-library-id`, `resolve_library_id`, `library-id-lookup`
- Query step: `query-docs`, `get-library-docs`, `docs-search`

### Context7 MCP (when available)

If your harness exposes Context7 MCP tools, use them directly. In this repo's Codex
tooling, the names are:

```
mcp__context7-mcp__resolve-library-id
mcp__context7-mcp__query-docs
```

If your harness uses different names, follow the same two-step flow above.

### Source Flow (btca / code search)

- Ask for **file paths and code snippets** so the answer is auditable.
- Prefer questions that return **where** and **how** (not just descriptions).
- Treat model summaries as hypotheses unless the response includes direct code evidence.

---

## When to Use Which

| Need | Use | Why |
|------|-----|-----|
| API signatures, params, docs examples | Documentation flow | Curated & authoritative |
| Behavior details, edge cases, internal patterns | Source flow | Real implementation |
| Verify a method exists | Documentation flow | Fast and reliable |
| Investigate bugs or unexpected behavior | Source flow + docs | Behavior often diverges |

---

## btca Notes (Reliability)

btca responses are generated by another model (e.g., Haiku 4.5) and can be wrong. Treat them as **assistant notes** unless backed by:
- a file path,
- a function/type name you can verify, and
- a snippet or direct pointer to the source.

**Best practice**: request “file path + relevant code excerpt” in every btca query.

---

## Usage Patterns

### Docs Lookup Pattern (tool‑agnostic)

- “Resolve canonical library ID for `<library>`.”
- “Query docs for `<specific API or behavior>`; return the exact signature and constraints.”

### btca Query Pattern

```bash
# Ask for auditable evidence
btca ask -r <resource> -q "Where is <thing> implemented? Provide file path + snippet."

# Interactive exploration
btca chat -r <resource>
```

**Good queries:**
- “Where is event emission implemented? Provide file path + relevant function.”
- “Show how spawn_blocking is scheduled; include file path + snippet.”

**Avoid:** “Explain how X works” with no request for file path/snippet.

---

## Evidence & Reporting Standard

When you report findings:
- **Label evidence**: `docs`, `source`, or `inference`.
- **Include the artifact**: link, file path, or snippet reference.
- **Note version/branch** if known.

Example:
- docs: “API signature from docs for `emit` (v2) …”
- source: “`crates/tauri/src/window.rs` shows …”
- inference: “Likely behavior based on … (needs verification)”
